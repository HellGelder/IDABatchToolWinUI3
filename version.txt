IDA BATCH TOOL (WinUI) - журнал версий сборки
==============================================
Формат записи: версия / дата / что изменилось.
Версия в свойствах exe должна совпадать с последней записью
(Directory.Build.props: Version / FileVersion - единый источник;
Package.appxmanifest и app.manifest синхронно; make-portable.ps1
и тест VersionConsistencyTests ловят расхождение).

1.0.0.32 / 2026-10-29
  Встроенная документация man-pages (Linux/Android) - скачивание man-pages удалено:
  - в поставку встраивается русская документация man-pages-ru (manpages-l10n 4.31.0)
    с английским fallback (man-pages 6.18), все секции 1-8, ~4000 страниц, ~4000
    функций в индексе; БД app\docs\manpages.db собирается на сборке
    (scripts\build-manpages.ps1, рендер roff->HTML через pandoc), приложение
    только читает; в настройках остался статус базы, кнопка «Скачать и
    импортировать» и автосинхронизация удалены (Workers/ManPagesSyncWorker,
    _python/manpages_bridge.py, конфиг-ключ manpages_db_path - ликвидированы);
  - документация показывается для ВСЕХ ELF-импортов: страница выбирается по
    приоритету секций (3 > 2 > 7 > ...), внутри секции русская страница
    предпочитается английской; английский fallback помечается «en», в отчёте -
    сноска с версиями корпусов и лицензиями (GPL-атрибуция, LICENSE в app\docs);
  - классификация модулей Linux/Android переработана под таксономию man-pages:
    словарь linux.py (~1800 строк) ликвидирован, «функция -> библиотека»
    берётся из секций LIBRARY man-страниц на этапе сборки БД; категории -
    строго по библиотекам man-pages (libc, libm, libpthread, librt, libdl,
    libresolv, libanl, libnsl, libcrypt, libutil), bionic/AOSP-словари вынесены
    в категорию «Системные библиотеки Android»; soname-канонизация для Android
    применяется только к бинарникам с ELF-заметкой android_api (libpthread,
    librt, libresolv и т.д. -> libc.so), для остальных - glibc-sonames;
  - sfa_function_index.db хранит android_api на файл (bionic/glibc вариант
    работает и в reuse-режиме); install-prereqs.ps1 больше не ставит requests.

1.0.0.30 / 2026-10-29

    безусловной

1.0.0.29 / 2026-10-29

    ОС» индекса общего анализа теперь считаются по одному множеству:
    уникальные импортированные библиотеки ОС + собственные библиотеки ОС
    из исследуемой директории. Раньше собственная библиотека ОС, которую
    никто не импортирует, учитывалась только в СФ

1.0.0.28 / 2026-10-29
  Исправлено:
  - is_system_module проверяла объединённый словарь платформы, из-за чего
    системными считались криптография (libcrypto/libssl), сеть (ws2_32),
    графика и среды выполнения (libgcc_s, msvcrt). Теперь «системная» -
    только категория «Системные библиотеки ОС»; критерий общий с
    is_sfa_module, поэтому счётчики индекса и анализа СФ совпадают
  - «Общий анализ»: каждый модуль попадает ровно в одну категорию
    классификатора. Собственный модуль помечается тегом «собственный»
    (раньше - «внутренняя») и дополнительно остаётся в «Внутренних модулях
    проекта» (тег «системная», если это библиотека ОС); импортированный -
    тегом «импортирована» в своей категории
  - сводка СФ: «Системных библиотек» = уникальные импортированные
    библиотеки ОС + собственные библиотеки ОС из исследуемой директории
    (раньше собственные не учитывались вовсе)

1.0.0.27 / 2026-10-29
  Исправлено:
  - «Анализ СФ» для Linux/Android считал системными все функции, у которых
    нашлась man-страница. Теперь системность определяет только словарь
    «Системные библиотеки ОС»: библиотека берётся из секции LIBRARY
    man-страницы (libc, libpthread, …) и проверяется по словарю. Функции из
    криптографии (libcrypto/libssl) и runtime (libgcc_s) системными не
    считаются - в колонке «Библиотека» теперь каноническое имя (libc.so.6),
    а не «-»
  - is_sfa_module проверяет категорию «Системные библиотеки ОС» для всех
    платформ, а не только для Windows: «Системных библиотек» в отчёте СФ
    больше не расходится с категорией в «Общем анализе» (было 10 против 7)
  - в классификаторе имён добавлена короткая форма библиотеки
    (libpthread.so.0 → libpthread) - без неё имена из man-страниц не
    сопоставлялись со словарями
  - мини-диспетчер задач: карточек потоков ровно столько, сколько выбрано
    потоков IDA. Раньше число карточек бралось как max(выполняющихся,
    выбранных), а события воркера несли только имя файла, из-за чего одна
    запись могла помечаться несколько раз

  Изменено:
  - «Общий анализ»: внутренняя библиотека показывается и в «Внутренних
    модулях проекта» (тег «системная», если словарь знает её как системную),
    и в своей системной категории (тег «внутренняя»); импортируемые системные
    библиотеки помечаются «импортирована»

1.0.0.26 / 2026-10-29
  Исправлено:
  - база man-pages импортировалась без единой функции (диалог «0 функций»):
    строка NAME man-страницы содержит roff-экранирование дефиса

    друга: ключ страницы теперь (page_name, section). Импорт пересоздаёт
    таблицы, хвосты старых прогонов не остаются
  - для Linux/Android база man-pages скачивается и импортируется
    автоматически при первом анализе СФ, если её нет или она пуста
    (без базы системность ELF-функций не определяется - в экспорте модуль
    импорта псевдо-модуль .dynsym - и отчёт показывал 0 системных функций)

  Изменено:
  - «Общий анализ»: библиотека, лежащая в исследуемой папке, больше не
    считается заведомо «внутренней» - системность проверяется по словарям
    выбранной платформы; системные попадают в свою категорию с тегом
    «внутренняя», импортируемые - с тегом «импортирована». Счётчик
    системных библиотек теперь совпадает с «Анализом СФ»
  - карточка «Модулей» в индексе показывает число уникальных зависимостей,
    а не число файлов

1.0.0.25 / 2026-10-29
  Исправлено:
  - генерация HTML-отчётов на встроенном Python падала с
    «ModuleNotFoundError: No module named 'classifier'» (и так же молча
    ломался разбор ELF-описаний: elf_descriptions). Причина: embeddable
    Python, который ставит install-prereqs.ps1 в app\Tools\Python, содержит
    файл pythonXY._pth - при его наличии sys.path собирается только из
    записей файла, и каталог запускаемого скрипта в него не попадает.
    Обычная системная установка Python каталог скрипта добавляет, поэтому
    ошибка проявлялась не у всех: у кого интерпретатор взят из
    app\Tools\Python - СФ-отчёты выдавали «отчётов 0/0» с трейсбеком.
    Мосты (report_bridge.py, manpages_bridge.py) теперь сами добавляют свой
    каталог в sys.path и не зависят от способа запуска интерпретатора
  - site-packages встроенного Python подключался по неверному относительному
    пути (на уровень выше app\Tools\Python); теперь проверяются оба варианта

1.0.0.23 / 2026-10-27
  Исправлено:
  - поиск документации MS Learn шёл фактически в один поток: общий клиент
    держал lock на всё время HTTP-запроса, поэтому 4 потока пула выстраивались
    в очередь. Замки сужены до состояния сессии, HTTP выполняется параллельно,
    соединение keep-alive на поток (TLS-рукопожатие не на каждый запрос),
    handshake при протухшей сессии делает один поток. Замер на 7 функциях:
    2,9 с вместо ~5 с; на больших наборах выигрыш пропорционален числу потоков
  - GUI «замирал» при генерации HTML СФ: мост печатает PROGRESS на каждую
    импортируемую функцию и каждый найденный документ, и тысячи обновлений
    забивали очередь UI-потока (окно не отвечало, диалог о завершении не
    успевал показаться, хотя HTML и индекс уже были записаны). Разбор stdout
    выведен с UI-потока (ConfigureAwait(false)), прогресс прореживается до
    4 обновлений в секунду с обязательной выдачей последнего сообщения перед
    Finished
  - диалог о завершении генерации СФ показывает проверяемые счётчики:
    отчётов (из файлов), системных функций, функций без документации и всего
    импортов - видно, что в HTML попали все функции из индекса/кэша
  Добавлено:
  - HtmlGenResult: total_system_functions / total_system_modules /
    total_system_notfound / total_imports из RESULT моста
