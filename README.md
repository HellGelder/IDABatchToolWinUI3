# IDA Batch Tool — WinUI 3 (исполнение 2)

Нативное Windows‑приложение для пакетного анализа бинарных файлов (PE / ELF / Mach‑O) через IDA Pro с генерацией HTML‑отчётов, сравнением бинарников (BinDiff + Diaphora) и анализом системных функций (СФ).

Это **второе исполнение** проекта `IDABatchTool`: вместо Python/Qt (PySide6) используется **C# / .NET 9 / WinUI 3** (Windows App SDK). Приложение полностью самодостаточно — собственные `config.yaml`, Python‑мосты (`_python/`) и скрипты (`scripts/`), без зависимости от пакета `ida_batch_tool` исполнения 1. Подробное описание общего пайплайна, отчётов и внешних инструментов (IDA, BinExport, BinDiff) — в [README исполнения 1](../IDABatchTool/README.md).

* **Пакетный анализ** — параллельный запуск нескольких копий `idat.exe`, крупные файлы первыми.
* **Автоэкспорт в JSON** — метаданные, функции, импорты, псевдокод (опционально).
* **HTML‑отчёты** — интерактивные Jinja2‑шаблоны, одинаковые с исполнением 1.
* **Сравнение директорий** — два движка на выбор: BinDiff, Diaphora или оба сразу; сопоставление пар по относительным путям.
* **Анализ СФ** — отчёты по системным функциям с документацией: Windows — Microsoft Learn (прямой MCP‑клиент), Linux/Android — man‑pages (локальная SQLite‑БД).
* **Поддержка архивов** — автоматическая распаковка APK, IPA (zip), DMG (7‑Zip).
* **Мини‑диспетчер задач** — живой монитор процессов IDA: PID, поток, CPU, память.
* **Современный UI** — WinUI 3 с Mica‑фоном, светлая/тёмная тема, системные уведомления.

|-----------|--------|------------|----------------|

| **BinDiff** | 8 standalone CLI | Движок сравнения (`bindiff.exe`) | Для вкладки «Сравнение» |
| **Python** | 3.10+ | Python‑мосты: отчёты (jinja2), man‑pages (requests), поиск MS Learn | Да |
| **jinja2 / requests** | — | Зависимости мостов (остальное — стандартная библиотека) | Да |
| **7‑Zip** | 23+ | Распаковка `.dmg` (APK/IPA распаковываются средствами .NET) | Только для DMG |
| **Node.js / npx** | 18+ | Фолбэк поиска документации MS Learn; основной путь — прямой MCP‑вызов из Python | Опционально |

Автопоиск инструментов: `idat.exe` / `bindiff.exe` ищутся по порядку — путь из `config.yaml` → реестр Windows (`Hex-Rays\IDA`, `Zynamics\BinDiff`, …) → `C:\Program Files` → `PATH` → рядом с приложением. Python ищется: `Tools\Python` рядом с приложением → `PATH` (`pythonw.exe` предпочтительнее) → Py Launcher. 7‑Zip: `Tools\7‑Zip` → `PATH` → `C:\Program Files\7‑Zip`.

# Быстрый старт (из исходников)

```bash
cd IDABatchToolWinUI
dotnet run
```

Решение (.sln) не используется — проект запускается напрямую через .NET CLI (или открытием `IDABatchToolWinUI.csproj` в Visual Studio 2022). При запуске контент (`_python/`, `scripts/`, `config.yaml`, `bindiff.exe`) копируется в выходную папку `bin\…` — приложение находит свой каталог по признаку «рядом есть `_python/`», поднимаясь вверх от exe.

При первом запуске:

1. Откройте вкладку **«Конфигурация»**, проверьте пути к `idat.exe` / `bindiff.exe` (кнопки автопоиска) и нажмите **«Сохранить»**.
2. Там же при необходимости синхронизируйте БД man‑pages (нужна для документации СФ на Linux/Android).
3. На вкладке **«Общий анализ»** укажите папку с бинарниками и запустите анализ.

# Сборка и публикация

## Отладка

```bash
dotnet build -c Debug -v quiet
dotnet run
```

## Release‑публикация и переносимая поставка

```bash
dotnet publish -c Release -r win-x64
# варианты RID: win-x86, win-x64, win-arm64 (по умолчанию — архитектура машины)
```

**Self-contained задан явно**: `make-portable.ps1` публикует с `-p:SelfContained=true`. Полагаться на умолчание «RID ⇒ self-contained» нельзя — без явного флага publish выходит framework-dependent (без рантайма .NET), и на машине без .NET 9 приложение требует его установки. Признак самодостаточной сборки: `coreclr.dll`/`hostfxr.dll` рядом с exe (zip ≈ 94 МБ, распаковано ≈ 240 МБ). `PublishReadyToRun` и `PublishTrimmed` **намеренно отключены** — они ломают WinRT-проецирование в рантайме (см. [Известные особенности](#известные-особенности-и-ограничения)). После обновления контентных файлов в `_python/`/`scripts/` не забывайте, что их включение в сборку задаётся явными масками `<Content>` в `IDABatchToolWinUI.csproj`.

### Готовая переносимая сборка (make-portable.ps1)

Скрипт собирает поставку с чистым корнем: publish → перекладка всего содержимого в `app\` → компиляция лончера → `bindiff.exe` в корень → zip.

```powershell
.\make-portable.ps1                # полный цикл: dist\portable\ + dist\IDABatchToolWinUI-<версия>.zip
.\make-portable.ps1 -NoPublish     # пересобрать раскладку из готового publish
.\make-portable.ps1 -NoZip         # без архивирования
.\make-portable.ps1 -Rid win-arm64 # другой RID
.\make-portable.ps1 -SkipGraph     # без актуализации графа graphify
```

Архив именуется по версии файла из csproj: `IDABatchToolWinUI-1.1.0.0.zip`. Скрипт встраивает в поставку `Tools\Python` из корня проекта, если он там есть; в корень пакета кладутся `README.txt` (требования), `version.txt` (журнал сборок) и `install-prereqs.ps1` — автоустановка Python-окружения. Приложение при запуске проверяет наличие Python и пакетов `jinja2`/`requests`; если чего-то нет — предлагает запустить автоустановку (при полном окружении никаких окон не появляется).

Раскладка результата:

```
portable/
├── IDABatchTool.exe               # лончер (~10 КБ): запускает app\IDABatchToolWinUI.exe
├── bindiff.exe                    # BinDiff CLI в корне поставки
└── app\                           # вся publish-папка: exe, все DLL, _python\, scripts\, config.yaml, Assets\
```

Лончер — 30 строк C#, компилируется системным компилятором .NET Framework (`csc.exe`, есть в любой Windows 10) с иконкой приложения и без добавления зависимостей; при отсутствии `app\IDABatchToolWinUI.exe` показывает сообщение об ошибке. Приложение внутри `app\` не меняется: оно находит свой каталог по `_python\` вверх от exe. Опциональные портативные утилиты кладутся в `app\Tools\` (`Tools\Python`, `Tools\7-Zip`). `ToolLocator` находит `bindiff.exe` и в `app\`, и в корне поставки.

DLL переносятся во вложенную папку именно таким косвенным путём: WinUI 3 не поддерживает single-file publish (нативные компоненты Windows App SDK обязаны лежать файлами на диске), а runtime-сборки self-contained приложения обязаны находиться рядом с exe.

На целевой машине нужны: Python 3 с `jinja2` и `requests` (либо встроенный Python из `app\Tools\Python`), IDA Pro и BinDiff (лицензионные — в поставку не включаются), 7‑Zip только для DMG.

## Граф знаний (graphify)

`make-portable.ps1` при полной сборке (не при `-NoPublish`) актуализирует **малый граф** проекта в `graphify-out/`: свой C#/XAML- и Python-код без вендоренной Diaphora. Шаг необязательный: `-SkipGraph` его пропускает, а отсутствие graphify даёт предупреждение, а не ошибку сборки. Первичная сборка выполняется автоматически, дальше используется инкрементальный `graphify update`.

В git коммитятся только `graphify-out/GRAPH_REPORT.md` (карта архитектуры) и `graphify-out/manifest.json` (перечень файлов корпуса); `graph.json`, `graph.html` и `cache/` остаются локальными. **Полный граф** — с вендоренной Diaphora — в git не попадает и обновляется по запросу:

```powershell
$env:GRAPHIFY_OUT = 'graphify-out-full'
graphify . --code-only
Remove-Item Env:GRAPHIFY_OUT
```

Запросы к готовому графу: `graphify query "<вопрос>"`, `graphify explain "DiffWorker"`, `graphify path "DiffPage" "DiffWorker"`.

# Интерфейс

Единое окно с верхней навигацией (NavigationView, Mica‑фон, системная иконка СФБ ЛАБ): три рабочих раздела и «Конфигурация» в правом углу. Страницы кэшируются — переключение вкладок не сбрасывает введённые пути и прогресс; во время активной задачи навигация на другие вкладки блокируется.

## Общий анализ

Полный цикл «папка с бинарниками → базы IDA → JSON → HTML‑отчёт».

1. **Скан папки** — рекурсивный поиск исполняемых файлов по всем платформенным расширениям; файлы без расширения распознаются по сигнатуре (MZ / ELF / Mach‑O magic). Найденные архивы APK/IPA/DMG автоматически распаковываются, содержимое включается в очередь. Платформа (Windows / Linux‑Android / macOS‑iOS) определяется автоматически по фактическому содержимому папки и показывается в InfoBar.
2. **Анализ в IDA** — параллельный запуск `idat.exe -B -P+` (ползунок «Одновременно IDA», по умолчанию 4; очередь сортируется по размеру — крупные файлы стартуют первыми). Результат — базы `.i64` рядом с исходниками.
3. **Экспорт JSON** — `idat -A -S export_data.py` по готовым базам: метаданные файла, функции, импорты, xref'ы; опция «псевдокод» добавляет декомпилированный код.
4. **Очистка** (опции) — удаление логов `.log`/`.asm`, временных файлов IDA (`.id0/.id1/.nam/.til`), JSON после генерации отчётов.
5. **HTML‑отчёт** — сводный индекс и частные отчёты по каждому файлу в `<входная папка>\IDAReports`; по завершении — системное уведомление и кнопка «Открыть папку».

Прогресс по фазам виден в строке статуса и на тремап‑полосе: каждый файл — блок, цвет = статус (серый — не анализировался, жёлтый — в работе, синий — успех, красный — ошибка). Кнопка «Подробнее» открывает [мини‑диспетчер задач](#мини-диспетчер-задач). Режим «экспорт без анализа» (`export_only`) позволяет догрузить JSON по уже готовым базам `.i64`/`.idb`.

## Сравнение (BinDiff + Diaphora)

Сравнение двух директорий с одинаковым набором модулей (например, две сборки одного продукта).

1. Укажите **левую** и **правую** директории (готовые базы `.i64`/`.idb`, в т.ч. от общего анализа) и папку результатов. Сопоставление пар — по относительным путям; таблица показывает совпавшие пары с чекбоксами выбора, размерами и счётчиками «только слева / только справа».
2. Выберите движок: **BinDiff**, **Diaphora** или **оба**. До 6 пар обрабатываются параллельно.
   Пары с побайтно идентичными бинарниками (совпадают размеры и содержимое файлов) в анализаторы не подаются вовсе: для них сразу пишется результат со схожестью 100%, статус «идентичен», отчёт помечается плашкой «Модули идентичны», доанализ не требуется.
3. Конвейер на каждую пару:
   - **BinExport** — `idat -OBinExportAutoAction:BinExportBinary` → `.BinExport` для обеих баз;
   - **BinDiff** — standalone `bindiff.exe` → база результатов `.BinDiff` + `.diff.json`;
   - **Diaphora** — экспорт `.sqlite` и сравнение штатным движком (копия Diaphora 3.4.2 в `scripts/diaphora/`) в облегчённом профиле: экспорт без микрокода (Hex‑Rays один раз на функцию, псевдокод‑эвристики сохранены), сравнение без медленных/экспериментальных/ненадёжных эвристик, таймаут эвристики 60 секунд — и в основном прогоне, и в доанализе;
   - **пост‑анализ** — hexdump‑diff, обогащение JSON (импорты, псевдокод парных функций), пересборка matched/unmatched по IDA‑экспорту как источнику истины (отсекаются псевдофункции BinExport).
4. **HTML‑отчёты** — сводный индекс `diff_index.html` и парные отчёты со степенью схожести в `<результаты>\Reports`; повторный прогон только Diaphora по существующим результатам («доанализ») пишется в `AddDiffResults\Reports`.

Статус каждой пары по каждому движку (`ожидает / анализ / завершён / ошибка / идентичен`) и PID текущего процесса видны прямо в таблице. Во время работы Diaphora в статусе пары каждые 30 секунд обновляется пульс: прошедшее время, ОЗУ процесса и размер БД («экспорт N мин, ОЗУ X ГБ, БД Y МБ» / «диф N мин, ОЗУ X ГБ, БД Y МБ»), для экспорта — ещё и прогресс из stdout Diaphora с оценкой остатка («…, 45% (осталось ~12 мин)»). Ограничений по времени работы Diaphora нет: живой процесс длится столько, сколько нужно (останов — только кнопкой «Отмена»). Контроль зависания — по факту работы: зависшим процесс считается, только если и ОЗУ, и БД (сумма .sqlite + *-wal + *-shm) не менялись дольше 4 часов; тогда процесс убивается, пара помечается ошибкой. Итог доанализа пишется в отчёт нейтральной плашкой: при неудаче — конкретная причина (какая фаза не состоялась, код выхода и хвост журнала Diaphora), при штатном сравнении без новых пар — «дополнительных пар не дал — все совпадения уже найдены BinDiff». Пары, у которых BinDiff не дал функций, а hexdump-схожесть 100%, на доанализ не попадают (файлы одинаковые). Схожести рядом с порогом 99% в отчётах отображаются честно: значение 98.97% так и показывается (а не округляется до «99.0%»).

### Git-сравнение (исходники)

Текстовый дифф двух директорий с исходниками в единый файл `changes.diff` (unified diff в стиле «git diff --no-index») — нативная реализация на C# (алгоритм Myers), вывод сверен с эталонным скриптом исполнения 1.

- Левая (старая) и правая (новая) директории, папка результата и glob-исключения.
- **Предварительная проверка контрольных сумм** — перед сравнением пары папок (в модульном режиме — папки каждого модуля) сверяются побайтово: наборы файлов с учётом исключений, размеры и содержимое. Идентичные папки не подаются на пофайловое сравнение — все файлы сразу «без изменений» (модуль получает статус «без изменений» без создания своей папки); факт пропуска фиксируется в журнале диффа.
- **«Полный дифф (все строки файлов)»** (по умолчанию снята) — размер диффа: отмечена — в дифф пишутся все строки файлов целиком, неизменённые участки не сжимаются; снята — стандартный контекст: 3 неизменённые строки вокруг каждого изменения.
- **«Сравнивать только исходные коды»** (включено по умолчанию) — файлы, распознанные как двоичные по содержимому, не попадают в дифф; они остаются в статистике и журнале. Снятие галки возвращает полный дифф.
- **«Сгенерировать HTML-отчёт»** — автономный `<имя>_report.html` рядом с `changes.diff`: офлайн-вьюер на diff2html (MIT, инлайн в HTML) со свёрнутым списком файлов (разворот по клику, ленивый рендер), режимами «рядом»/«строками», статусами файлов и счётчиками изменений.

#### Модульное сравнение

Галка «Модульное сравнение» (по умолчанию — авто: подпапки во входных папках есть → модульный режим) включает сравнение **по модулям**: каждая подпапка первого уровня OLD/NEW — отдельный программный модуль, пары сопоставляются по имени.

- Дифф строится отдельно по каждому модулю: `outDir\<модуль>\changes.diff` + журнал + частный HTML-отчёт `changes_report.html` рядом.
- Индексный отчёт `outDir\git_index.html` — сводка по всем модулям: сколько файлов изменено/добавлено/удалено, статус (изменён / новый / удалён целиком / без изменений / ошибка) и переходы на частный отчёт и `changes.diff` модуля; строка «Итого». Итоги сохраняются в `modules.json` — кнопка отчёта работает и после перезапуска приложения.
- Модуль, существующий только с одной стороны, сравнивается как «новый» или «удалён» целиком; модуль без текстовых изменений получает строку «без изменений» без своей папки. Файлы в корне OLD/NEW (вне подпапок-модулей) не сравниваются — пометка в журнале.
- Сравнение модулей выполняется в **4 потока** (не больше числа модулей): модули делятся на пулы по размеру (крупные вперёд), каждый поток обрабатывает только свой пул, а освободившийся поток атомарно забирает ещё не начатые модули. Прогресс — карточки потоков и счётчик «Готово X/N».

## Анализ СФ (системных функций)

Отчёты о том, какие **системные библиотеки ОС** и их функции использует каждый бинарник, с подгрузкой документации по функциям.

- В анализ берётся категория **«Системные библиотеки ОС»** из классификатора импортов (Python‑пакет `_python/classifier`: Windows, Linux, Android, macOS, сторонние модули — сверен с эталоном исполнения 1).
- **Документация Windows** — Microsoft Learn: мост обращается напрямую к MCP‑эндпоинту `learn.microsoft.com/api/mcp` (быстро, Node не нужен); `npx @microsoft/learn-cli` остался фолбэком. Результаты кэшируются в `<входная папка>\SFAReports\mslearn_cache.db` — при повторных прогонах сеть не используется. Если кэш уже существует, при запуске анализа предлагается выбор: полный поиск или перегенерация HTML из кэша.
- **Документация Linux/Android** — man‑pages: локальная SQLite‑БД (`manpages.db`, схема `pages`/`function_index`), скачивается и импортируется с kernel.org на вкладке «Конфигурация».
- Отчёты — в `<входная папка>\SFAReports`: сводный индекс и частные отчёты с описаниями функций, кэш‑статистика («найдено / в кэше»).

## Конфигурация

- Пути `idat.exe` / `bindiff.exe` — вручную или автопоиском (см. порядок выше).
- Тема оформления — светлая/тёмная, применяется сразу, сохраняется в `config.yaml`.
- **Проверка утилит** — 7‑Zip и Node.js/npx с валидацией версий (поиск строго по полным путям, чтобы случайная утилита из рабочего каталога не маскировала системную).
- **БД man‑pages** — выбор пути, проверка, фоновая синхронизация с прогрессом и отменой.

## Мини‑диспетчер задач

Отдельное окно (кнопка «Подробнее» на вкладке «Общий анализ»): очередь анализа с обновлением раз в секунду.

- По каждому файлу — статус (в ожидании / анализируется / завершён / ошибка / отменён), фаза (анализ / экспорт), PID процесса `idat.exe`, снимок процесса: процессорное время, память, число потоков ОС.
- Карточки пула рабочих потоков над таблицей: сколько слотов занято (подсвечены акцентом) и какой файл в каждом обрабатывается.
- Анализируемые файлы держатся вверху таблицы, завершённые опускаются вниз; итоговая сводка сессии — счётчики по всем статусам.

# HTML‑отчёты

Три типа отчётов генерирует Python‑мост `_python/report_bridge.py` по одним и тем же Jinja2‑шаблонам (`_python/templates/`), что даёт визуальную идентичность с исполнением 1. Внешние библиотеки (DataTables, marked) инлайнятся в HTML из `_python/vendor/` — отчёты открываются локально, без интернета. Отчёт Git‑сравнения собирается нативно на C# из того же каталога шаблонов и вендора (в HTML инлайнится diff2html).

| Тип | Куда пишется | Состав |
|-----|--------------|--------|
| Общий анализ | `<вход>\IDAReports` | `index.html` + частный отчёт на файл |
| СФ | `<вход>\SFAReports` | индекс + частные отчёты, кэши `mslearn_cache.db`, `sfa_function_index.db`, `manpages.db` |
| Сравнение | `<результаты>\Reports` | `diff_index.html` + парные отчёты; в частных — обратная ссылка на индекс (детерминированная, работает и при первом прогоне) |
| Git-сравнение | рядом с `changes.diff` | `<имя>_report.html` — автономный вьюер diff2html: свёрнутый список файлов, режимы «рядом»/«строками» |
| Git-сравнение (модульное) | корень папки результата | `git_index.html` — сводка по модулям (счётчики, статусы, переходы) + `<модуль>\changes_report.html` |

```
MainWindow (NavigationView, кэш страниц, блокировка навигации при работе)
 ├─ Pages/AnalysisPage ── Workers/AnalysisWorker ── Services/IdaRunner ── idat.exe
 │        │                  (фазы analysis → export)
```

**Каталоги:**

| Каталог | Содержимое |
|---------|-----------|
| `Pages/` | Четыре страницы UI (XAML + code‑behind), подписки на события — в конструкторе (страницы кэшируются) |
| `Workers/` | Фоновые задачи: `AnalysisWorker` (анализ + экспорт), `DiffWorker` (конвейер сравнения, до 6 параллельных пар), `HtmlGenWorker` (Python‑мост отчётов), `ManPagesSyncWorker` (синхронизация man‑pages) |
| `Services/` | `AppConstants` (пути, поиск Python, платформы и детект по сигнатурам), `ConfigService` + `MiniYaml` (собственный YAML‑парсер), `ToolLocator` (автопоиск idat/bindiff), `ExecutableFinder` (поиск исполняемых по расширениям/сигнатурам, отказоустойчивый обход каталогов), `ArchiveHandler` (APK/IPA/DMG), `IdaRunner` (пакетный запуск idat с отменой и очисткой), `AnalysisMonitor` (общее состояние очереди для диспетчера), `UiDialogs` (пикеры/диалоги), `AppNotifier` (toast‑уведомления) |
| `Models/` | `FileItem` (элемент очереди/тремапа), `DiffPair` (пара для сравнения), `PairRowViewModel` (строка таблицы пар, INPC для `x:Bind`) |
| `Controls/` | `TreemapControl` — полоса статусов анализа по числу файлов |
| `Helpers/` | Зарезервировано |
| `_python/` | Python‑мосты: `report_bridge.py`, `manpages_bridge.py`, `elf_descriptions.py`, пакет `classifier/`, шаблоны `templates/`, vendor‑ассеты `vendor/` |
| `scripts/` | `export_data.py` (IDAPython‑экспорт) и полный Diaphora (`scripts/diaphora/`) |
| `Assets/` | Иконки, `AppIcon.ico` (иконка exe и заголовка окна) |

**Ключевые решения:**

- **Потоковая модель.** Все сканы папок и тяжёлые операции — вне UI‑потока (`Task.Run`); события воркеров диспетчатся на UI через `DispatcherQueue`. Сканы с дебаунсом (400 мс) на изменение пути, защита от гонок устаревших сканов через «поколения».
- **Отмена.** Единый `CancellationToken` на всю цепочку: `IdaRunner` убивает дерево процессов IDA, `HtmlGenWorker` шлёт мосту строку `CANCEL` в stdin (мост завершает дочерние процессы сам) со страховочным `Kill(entireProcessTree)` через 5 секунд.
- **Протокол Python‑мостов.** Строгий текстовый протокол по stdout: `PROGRESS <cur> <total> <msg>`, `ERROR <msg>`, `RESULT <json>` (у man‑pages — `DONE <path>`). Каналы принудительно UTF‑8 (`PYTHONUTF8=1`), иначе pythonw пишет cp1251 и русский текст в GUI ломается. Успех фиксируется только по явному финальному сообщению, не по коду выхода.
- **Отказоустойчивость.** Обход каталогов переживает недоступные подпапки; невалидный YAML не ломает запуск; ошибки процессов не теряют финальное событие `Finished` (страница не зависает в «выполняется»); повторяющиеся имена файлов в очереди обновляются все, а не только первая запись.
- **Самодостаточность.** `AppConstants.ResolveWinUiDir()` находит каталог приложения (по `_python/` вверх от exe), поэтому работает и запуск из исходников, и переносимая поставка.

# Известные особенности и ограничения

- **`PublishReadyToRun` и `PublishTrimmed` отключены** (csproj, 2026-10-05): R2R-образы и триммер ломают рефлексивный механизм заворачивания управляемых объектов в WinRT-интерфейсы (`WinRT.TypeExtensions.GetAbiToProjectionVftblPtr` → `NullReferenceException` → нативный краш `0xc000027b` в `Microsoft.UI.Xaml.dll`). Симптомы на собранной поставке: пустая таблица пар на вкладке «Сравнение» и падение окна при развороте на весь экран. Подтверждено экспериментально (publish без R2R работает, с R2R — падает); R2R даёт лишь ускорение старта, поэтому отключение безопасно. Если включать обратно — обязательно перепроверять все экраны на собранной поставке, а не в Debug.
- **`app-crash.log`** — необработанные исключения XAML (в журнале событий Windows они выглядят как немой нативный краш) дублируются в этот лог рядом с exe: тип, сообщение и стек. Полезно при диагностике проблем на машинах пользователей.
- **Пикеры файлов/папок** — только `Microsoft.Windows.Storage.Pickers` (Windows App SDK 2.4, конструктор с `WindowId`); legacy‑пикеры с `FileTypeFilter` в этой версии вызывают `E_FAIL`.
- **Дубликаты имён файлов** в очереди анализа (файлы в подпапках/архивах) намеренно обновляются все — иначе «вторые» копии оставались в статусе «В ожидании».
- **Кириллица в протоколе мостов** — только через `PYTHONUTF8=1`/`PYTHONIOENCODING=utf-8`; при отладке мостов вручную из консоли учитывайте кодировку.
- **IDA/BinDiff не распространяются** вместе с приложением (лицензии Hex‑Rays/Google); на целевой машине нужны их установки, пути задаются в «Конфигурации».
